# Secret Handling di CI/CD: Riset untuk Distributed Software Factory

Status: SELESAI (dengan beberapa gap terverifikasi eksplisit di penutup — lihat "Gap riset yang belum terverifikasi").

Setiap klaim ditandai:
- **[VERIFIED-DOC]** — dari dokumentasi resmi / source code publik yang dicek langsung.
- **[IMPRESSION]** — kesan dari ringkasan pihak ketiga, belum dicek ke source primer.

## Konteks singkat (untuk pemetaan istilah)

Sistem kami: **Runner** (outbound-only, di belakang NAT) menjalankan **StepRun** di dalam **Sandbox** tempat **Agent** (Claude Code dkk) bekerja dengan kode ter-checkout. **Principal** (User atau ServiceAccount) memegang credential, menempel ke **Project** — bukan ke Run. **Repository** adalah anggota Project; **Git Remote** adalah bus perpindahan kode, tiap StepRun push ke **Branch**.

Perbedaan kunci vs CI biasa: Runner kami menjalankan AI coding agent yang mengeksekusi perintah arbitrer dan mencetak ribuan baris log — bukan skrip build tetap. Riset sebelumnya (sandcastle) menemukan **tidak ada redaksi log sama sekali**.

## 1. GitHub Actions

### 1.1 Penyimpanan
- **[VERIFIED-DOC]** Secret dienkripsi client-side pakai **Libsodium sealed box** sebelum dikirim ke GitHub (dari UI atau REST API) — jadi nilai plaintext tidak pernah menyentuh jaringan GitHub dalam bentuk terbuka saat submit. ([docs.github.com/actions/concepts/security/secrets](https://docs.github.com/en/actions/concepts/security/secrets))
- **[VERIFIED-DOC]** Setelah tersimpan, secret tetap terenkripsi sampai dipakai oleh Actions/Dependabot/Codespaces — didekripsi hanya saat run-time untuk disuntik ke job.
- **[IMPRESSION]** GitHub tidak menerbitkan detail publik soal manajemen key encryption-at-rest untuk GitHub.com (di mana master key disimpan, HSM dsb) — ini bagian tertutup dari infrastrukturnya. Untuk GHES (self-host), dokumentasi publik yang saya temukan tidak merinci bootstrap key encryption Actions secrets secara eksplisit; tidak sempat diverifikasi lebih jauh dalam riset ini.

### 1.2 Scoping
- **[VERIFIED-DOC]** Tiga level: **repository**, **organization** (bisa dibatasi ke repo/tipe repo tertentu lewat policy), dan **environment** (bisa mensyaratkan approval reviewer sebelum job dapat akses).
- Pemetaan ke model kami: level *environment* GitHub kira-kira setara **Project** — unit isolasi tempat secret menempel. Tidak ada konsep "per-Principal credential" di GitHub Actions — semua job dalam scope yang sama memakai secret yang sama, beda dengan model kami di mana Principal (User/ServiceAccount) berbeda punya credential berbeda.

### 1.3 Pengantaran ke Runner
- **[VERIFIED-DOC]** Runner (termasuk **self-hosted runner** — paralel langsung dengan Runner kami) **tidak menerima koneksi masuk sama sekali**. Listener pada runner membuka **HTTPS long-poll outbound** ke GitHub Actions Service (timeout ~50 detik, lalu buka long-poll baru), menunggu pesan "Job Available". Hanya perlu outbound port 443 — cocok untuk runner di belakang NAT. ([Depot.dev: GitHub Actions Runner architecture](https://depot.dev/blog/github-actions-runner-architecture-part-1-the-listener))
- **[IMPRESSION]** Begitu job diambil, secret yang di-scope ke job tersebut ikut dikirim sebagai bagian dari job message lewat koneksi HTTPS yang sama (bukan file terpisah di-mount, bukan sistem token-sekali-pakai yang diambil lewat request kedua) — lalu Actions runner worker menyuntikkannya sebagai environment variable ke proses step. Detail persis payload job message tidak saya temukan didokumentasikan publik secara resmi; ini kesan dari gabungan artikel arsitektur pihak ketiga, bukan dari source code `actions/runner` yang saya baca langsung.
- Relevansi untuk kami: pola **"runner poll keluar, dapat job + secret dalam satu response"** adalah pola yang paling cocok untuk Runner outbound-only kami — tidak perlu control plane menghubungi balik Runner untuk sesi pengambilan secret terpisah.

### 1.4 Redaksi log — bagian kritis
- **[VERIFIED-DOC]** Redaksi terjadi **di sisi Actions service / UI saat render log**, berbasis **exact string match** terhadap nilai secret yang terdaftar. Ada juga command manual `::add-mask::VALUE` yang bisa dipanggil step untuk mendaftarkan nilai turunan sebagai secret baru.
- **[VERIFIED-DOC]** Dokumentasi resmi eksplisit bilang: **"automatic redaction is not guaranteed."**
- **[VERIFIED-DOC]** Mode kegagalan yang didokumentasikan resmi:
  - **Structured data** (JSON/XML/YAML yang membungkus secret) bikin redaksi gagal karena match harus exact terhadap seluruh string yang terdaftar sebagai secret.
  - **Transformasi** (base64, URL-encode) menghasilkan string berbeda dari nilai asli → tidak match → tidak ter-mask. Guidance resmi: kalau secret ditransformasi, register hasil transformasinya sebagai secret baru juga.
  - **Error output ke STDOUT/STDERR** dari tool pihak ketiga yang tidak terduga bisa membocorkan secret tanpa developer sadar.
  - **Derived secrets** (mis. JWT yang ditandatangani pakai private key secret) harus didaftarkan manual sebagai secret kalau mau ter-mask.
  - Remediasi resmi kalau bocor: **hapus log run dan rotate secret** — tidak ada mekanisme "tarik kembali" yang lebih halus.
- **[IMPRESSION — dari blog pihak ketiga, bukan sumber resmi]** Detail kegagalan konkret tambahan (belum diverifikasi ke source code):
  - Base64 4-char alignment bikin secret pendek yang di-encode utuh tetap tidak match walau secretnya sendiri ter-registrasi (encoding base64 tidak selalu align byte boundary yang sama dengan representasi teks asli).
  - JSON yang di-reformat lewat `jq` (whitespace/newline berubah) memecah exact-match jadi beberapa baris yang tak satu pun cocok persis dengan string asli.
  - Secret pendek (di bawah ~3-4 karakter) **sengaja tidak di-mask** oleh GitHub karena kalau dipaksa, terlalu banyak string umum di log berubah jadi asterisk (terlalu banyak false-positive) — implikasinya: secret pendek nyaris tidak terlindungi.
  - Tidak ada laporan insiden publik terdokumentasi dengan detail forensik yang saya temukan — kebanyakan sumber sifatnya penjelasan mekanisme + skenario hipotetis, bukan post-mortem nyata bernama.
- **Kesimpulan arsitektural**: GitHub Actions memasang redaksi **di control plane, saat serving log ke UI/API** (bukan di runner sebelum log dikirim) — jadi nilai mentah **sempat melintasi jaringan** dari runner ke GitHub, dan tersimpan mentah di storage log GitHub (baru disensor saat ditampilkan). Ini persis trade-off yang disebut di brief: bisa diperbaiki belakangan (re-render setelah register secret baru), tapi nilai mentah sempat transit dan tersimpan di server.

### 1.5 Akses repo (clone privat, push branch)
- **[VERIFIED-DOC]** Setiap job otomatis dapat `GITHUB_TOKEN` — token **berumur pendek, dibuat ulang tiap job, expire saat job selesai** (default; ada masalah dilaporkan di mana token bisa lebih lama hidup dari yang diharapkan pada workflow tertentu — lihat catatan nopcorn di bawah). Scope dan permission token ini bisa dibatasi lewat `permissions:` di workflow YAML (least privilege per-job, bagian dari file yang sama dengan definisi pipeline).
- **[IMPRESSION — dari artikel security researcher nopcorn, belum saya cross-check ke source `actions/runner`]** Artikel "GITHUB_TOKEN isn't that Ephemeral" mengklaim token ini praktiknya bisa tetap valid lebih lama dari sekadar "durasi job" dalam kondisi tertentu (mis. job yang menahan token lalu dipakai setelah job "selesai" secara logis) — ini catatan risiko implementasi, bukan cacat desain resmi yang diakui GitHub secara terbuka.
- **[VERIFIED-DOC]** Untuk kebutuhan lintas-repo (bukan repo tempat workflow jalan): rekomendasi resmi & komunitas mengarah ke **GitHub App installation token** — token berumur pendek (~1 jam), scope granular per-repository & per-permission, gampang di-install/uninstall dari repo tertentu, dan tidak terikat ke akun manusia.
- **[IMPRESSION]** Perbandingan 3 opsi (dari artikel security-hardening pihak ketiga, konsisten dengan pemahaman umum GitHub):
  - **PAT (classic/fine-grained)**: gampang dibuat, tapi **terikat identitas user** (bukan Principal non-manusia yang jelas), classic PAT bisa never-expire, fine-grained PAT default expiry 1 tahun — risiko operasional tinggi kalau orangnya keluar tim karena token tidak otomatis dicabut oleh proses offboarding standar kecuali eksplisit di-manage.
  - **Deploy key**: SSH keypair, private key disimpan di CI, **scope ke satu repo, read-only secara default** (write butuh diaktifkan eksplisit), **tidak ada expiry bawaan** — cocok untuk kasus sederhana satu-repo tapi tidak scalable untuk banyak repo dan tidak short-lived.
  - **GitHub App installation token**: token pendek, scope granular, **direkomendasikan** untuk kebutuhan multi-repo / production CI.
- **Git host self-hosted (Gitea/Forgejo) belum tercakup di bagian ini** — dibahas terpisah di §6 karena bukan bagian dari GitHub Actions itu sendiri.

### 1.6 Masa hidup & pencabutan
- **[VERIFIED-DOC]** **Just-in-Time (JIT) runner** — pola untuk self-hosted runner: registration token dibuat lewat API (`POST /orgs/{org}/actions/runners/registration-token` atau varian JIT config), token itu **sekali pakai untuk registrasi**, runner yang didaftarkan lewat token ini **hanya boleh menjalankan satu job lalu otomatis di-deregister** oleh GitHub Actions service. Tujuannya eksplisit: **membatasi exposure credential jangka panjang** di infrastruktur runner.
- **[VERIFIED-DOC]** `GITHUB_TOKEN` per-job: expire otomatis saat job selesai (model normal); ada laporan edge-case (lihat 1.5) di mana ini tidak seketat yang diharapkan pada skenario tertentu.
- **[IMPRESSION]** Tidak ada dokumentasi resmi yang saya temukan soal skenario **"Runner dicurigai bocor → cabut semua credential yang pernah lewat runner itu"** sebagai fitur satu-tombol. Mitigasinya lebih ke arah: hapus/deregister runner, rotate semua secret yang berada di scope (repo/org/env) yang pernah diakses runner itu — manual, bukan otomatis dari sisi platform.

### 1.7 OIDC token exchange (khusus diminta di brief)
- **[VERIFIED-DOC]** Alternatif untuk **tidak menyimpan secret cloud sama sekali**: workflow minta token OIDC pendek dari GitHub's OIDC provider (berisi klaim identitas job — repo, workflow, ref, environment dsb), lalu **tukar token itu** ke STS/token-endpoint cloud provider (AWS STS `AssumeRoleWithWebIdentity`, Azure AD, GCP Workload Identity Federation). Cloud provider mem-validasi klaim (trust policy) dan menerbitkan **credential sungguhan yang berumur pendek** (umumnya 15 menit–1 jam, atau habis saat job selesai).
- **[VERIFIED-DOC]** Manfaat inti: **tidak ada long-lived cloud credential yang disimpan sebagai GitHub secret sama sekali** — trust relationship dikonfigurasi di sisi cloud provider (siapa yang boleh assume role, berdasarkan klaim OIDC), bukan credential yang disalin-tempel ke secret store.
- **Relevansi untuk kami**: pola ini paling pas untuk **credential cloud** (AWS/GCP/Azure) yang dipakai StepRun untuk deploy dsb — Runner tidak perlu pernah memegang API key cloud jangka panjang, cukup token OIDC pendek dari control plane kami sendiri (kalau kami bangun token issuer serupa) yang ditukar tepat sebelum dipakai. **Tidak langsung applicable** ke secret arbitrer (API key pihak ketiga yang tidak mendukung OIDC/federation) — mayoritas secret yang dipegang AI coding agent (API key model, PAT internal tool) kemungkinan besar tidak punya token-exchange endpoint, jadi OIDC menyelesaikan sebagian kecil masalah kami, bukan semua.

## 2. Woodpecker CI

### 2.1 Penyimpanan
- **[VERIFIED-DOC]** Enkripsi at-rest itu **opsional**, diaktifkan lewat `WOODPECKER_ENCRYPTION_KEY` di server config. Kalau tidak diset, secret **tersimpan plaintext** di database (SQLite/MySQL/PostgreSQL) — beda dari GitHub Actions yang selalu terenkripsi.
- **[IMPRESSION]** Marketing page Woodpecker menyebut "256-bit AES with GCM" untuk data at-rest, tapi dokumentasi teknis resmi yang saya baca (server config, secrets page) tidak menyebut algoritma spesifik di halaman yang sama — jadi klaim algoritma ini datang dari halaman marketing (`woodpecker.co/safety-security`), bukan referensi konfigurasi teknis. Konsisten dengan kesan umum (AES-GCM) tapi belum saya verifikasi ke source code langsung.
- **[VERIFIED-DOC]** Key dimuat saat **server startup** dan dipakai transparan oleh store layer untuk encrypt/decrypt. Bootstrap key itu sendiri (`WOODPECKER_ENCRYPTION_KEY`) adalah tanggung jawab operator — biasanya env var / secret file yang di-inject manual ke proses server, tidak ada mekanisme built-in seperti KMS/HSM terintegrasi.
- **[IMPRESSION]** Tidak ada integrasi resmi ke Vault/SOPS/age yang saya temukan didokumentasikan — Woodpecker punya konsep **"secret extension"** (webhook endpoint eksternal yang dipanggil server untuk resolve secret saat runtime), yang secara arsitektural bisa dipakai untuk mem-proxy ke Vault dsb, tapi ini pola "bangun sendiri integrasinya", bukan plugin resmi siap pakai untuk Vault/SOPS/age.

### 2.2 Scoping
- **[VERIFIED-DOC]** Tiga tingkat: **repository**, **organization**, **global** (instance-wide, hanya admin instance yang bisa buat). Prioritas: repo > org > global kalau nama sama.
- **[VERIFIED-DOC]** Secret **tidak otomatis terekspos ke pull request** dari luar (defaultnya off untuk PR event) — mitigasi untuk kasus repo publik dengan kontribusi eksternal, mirip Drone.
- **[VERIFIED-DOC]** Ada fitur **restrict secret ke plugin/image tertentu** — kalau diaktifkan, secret itu hanya terlihat oleh image yang di-whitelist. Rasionalnya eksplisit didokumentasikan: **plugin (image yang sudah dikenal) tidak bisa eksekusi perintah arbitrer, jadi tidak bisa membocorkan secret** — asumsi ini eksplisit menyebut ancaman "arbitrary command execution" yang sangat relevan ke kasus kami (di mana Sandbox kami justru *dirancang* untuk eksekusi perintah arbitrer oleh Agent).
- Pemetaan ke model kami: scope repo/org/global Woodpecker tidak punya konsep Principal terpisah — mirip GitHub Actions, semua job dalam scope yang sama share akses secret yang sama, tidak per-Principal seperti model kami.

### 2.3 Pengantaran ke Runner (Agent)
- **[VERIFIED-DOC]** Agent (setara Runner kami) membuka **koneksi gRPC outbound** ke server, opsional TLS (`WOODPECKER_GRPC_SECURE`). Sama seperti GitHub Actions self-hosted runner: **outbound-only**, tidak butuh inbound port di belakang NAT.
- **[VERIFIED-DOC]** Autentikasi agent pakai shared secret (`WOODPECKER_AGENT_SECRET`) — bisa system-wide token atau token unik per-agent yang dibuat lewat UI. Ini token identitas Runner, bukan secret pipeline.
- **[IMPRESSION]** Detail persis bagaimana secret pipeline (bukan token agent) disuntik dari server → agent → container step tidak terdokumentasi eksplisit di halaman yang saya baca; berdasarkan pola gRPC + `from_secret` di YAML, kesan saya secret dikirim sebagai bagian dari definisi job (gRPC message) saat agent mengambil job, lalu agent yang menyuntikkan sebagai env var ke container step — pola "job pull membawa secret sekaligus", sama seperti GitHub Actions self-hosted, bukan token-sekali-pakai terpisah maupun file-mount dari server.

### 2.4 Redaksi log
- **[VERIFIED-DOC — temuan paling penting]** Woodpecker **hanya bisa mask secret yang berasal dari secret store-nya sendiri**. Dokumentasi eksplisit bilang: *"Woodpecker can mask secrets from its own secrets store, but it cannot apply the same protection to external secrets."* Artinya kalau Agent (dalam kasus kami: AI coding agent) mencetak sesuatu yang kebetulan mengandung nilai sensitif yang **bukan** terdaftar sebagai Woodpecker secret (mis. token yang di-generate di dalam Sandbox, atau credential dari sumber lain), **tidak ada mekanisme perlindungan sama sekali** — ini prinsip yang sama seperti "exact string match" GitHub Actions, tapi scope-nya lebih sempit (hanya string yang terdaftar sebagai Woodpecker secret, bukan string arbitrer yang di-mask manual seperti `::add-mask::` GitHub).
- **[IMPRESSION]** Tidak saya temukan dokumentasi resmi soal *di mana* redaksi terjadi (server saat serve log ke UI, atau agent sebelum kirim log stream ke server). Berdasarkan arsitektur gRPC streaming log dari agent ke server, kemungkinan besar log stream dikirim mentah dari agent lalu disensor di server sebelum ditampilkan (pola sama seperti GitHub Actions) — tapi ini dugaan arsitektural, belum saya verifikasi ke source code.

### 2.5 Akses repo
- **[IMPRESSION]** Tidak ada halaman resmi spesifik yang saya baca langsung soal mekanisme clone/push Woodpecker (deploy key vs token forge). Dari pengalaman umum ekosistem Drone/Woodpecker: server menyimpan OAuth token forge (GitHub/Gitea/GitLab/Forgejo) milik user yang menghubungkan repo, lalu meneruskan token itu (atau men-generate deploy key) ke agent untuk clone. Klaim ini **belum diverifikasi ke dokumentasi resmi** dalam sesi riset ini — tandai sebagai gap.

## 3. Drone CI

*(Drone adalah nenek moyang Woodpecker — arsitektur mirip; catatan di bawah fokus ke perbedaan.)*

### 3.1 Penyimpanan
- **[VERIFIED-DOC]** Dua mekanisme berbeda dan terpisah:
  1. **Database secrets** — diaktifkan lewat `DRONE_DATABASE_SECRET`, yang mengenkripsi secret di database server. **Encryption disabled by default**, harus dikonfigurasi **sebelum sistem pertama kali dipakai** (tidak ada migrasi otomatis retroaktif yang disebutkan — implikasinya: mengaktifkan enkripsi belakangan pada instalasi lama butuh langkah manual/migrasi data).
  2. **Encrypted secrets (file-based)** — secret dienkripsi lewat CLI (`drone encrypt <repo> <secret>`) dengan **AES-GCM, key unik per-repository**, key tersebut **tidak pernah keluar dari server** (server-side only). Hasil enkripsi disimpan sebagai string terenkripsi langsung di file YAML pipeline (masuk git repo, bukan di database terpisah) — jadi secret ter-versioning bersama kode, tapi tetap terenkripsi.
- Pola kedua ini menarik: **secret hidup di repo (sebagai ciphertext), key hidup di server** — mirip prinsip envelope encryption sederhana, dan menghindari masalah "siapa yang boleh lihat secret store terpisah" karena akses baca ciphertext = akses baca repo (yang sudah dikontrol lewat permission git biasa), sementara kemampuan decrypt tetap terpusat di server.

### 3.2 Scoping
- **[VERIFIED-DOC]** Default Drone: secret **available ke semua repo dan semua build event** — permisif secara default, harus **secara eksplisit dibatasi**. Dibatasi lewat anotasi `X-Drone-Repos` dan `X-Drone-Events` pada definisi secret.
- **[VERIFIED-DOC]** Secret juga bisa dibatasi ke **image Docker tertentu** lewat flag `--image` — mirip fitur "restrict ke plugin" Woodpecker, prinsip sama: batasi secret ke proses yang punya permukaan eksekusi terbatas.
- **[VERIFIED-DOC]** Secret **tidak diekspos ke pull request dari fork** — mitigasi standar di ekosistem Drone/Woodpecker untuk repo publik.
- Catatan desain: default permisif ("semua repo bisa lihat semua secret kecuali dibatasi") adalah **kebalikan** dari prinsip least-privilege yang kami mau — di model kami, secret menempel ke Project dan defaultnya harus deny-by-default lintas Project, bukan allow-by-default yang perlu di-annotate manual untuk dipersempit.

### 3.3 Akses ke secret manager eksternal
- **[VERIFIED-DOC]** Drone punya konsep **secret plugin** — server memanggil endpoint eksternal (`DRONE_SECRET_PLUGIN_ENDPOINT`, diautentikasi dengan `DRONE_SECRET_PLUGIN_TOKEN`) untuk resolve secret saat runtime, alih-alih menyimpan sendiri. ("Drone Vault" adalah implementasi resmi pola ini untuk HashiCorp Vault, diumumkan lewat blog resmi Drone.)
- Ini pola "pull, bukan push": server Drone tidak menyimpan nilai secret Vault sama sekali, hanya menyimpan *referensi* dan menariknya on-demand — mengurangi permukaan kebocoran di database Drone sendiri, tapi menambah dependency operasional (Vault harus selalu tersedia saat build jalan) dan menambah satu network hop lagi yang bisa jadi titik gagal/log.

### 3.4 Redaksi & akses repo
- **[IMPRESSION]** Tidak ada dokumentasi resmi spesifik soal mekanisme redaksi log Drone yang saya baca langsung dalam sesi ini — berbeda dari Woodpecker yang eksplisit mendokumentasikan keterbatasan "hanya mask secret dari store sendiri". Drone kemungkinan besar mewarisi pola serupa (Woodpecker adalah fork Drone versi lama) tapi ini **dugaan berdasarkan silsilah kode, bukan verifikasi langsung** — gap riset.
- **[IMPRESSION]** Mekanisme clone/push repo tidak sempat diverifikasi ke dokumentasi resmi dalam sesi ini — gap riset yang sama seperti Woodpecker.

Sumber: [docs.drone.io — Encrypted secrets](https://docs.drone.io/secret/encrypted/), [github.com/drone/docs — drone-database-secret.md](https://github.com/drone/docs/blob/master/content/server/reference/drone-database-secret.md), [blog.drone.io — Announcing Vault Secrets](https://blog.drone.io/drone-vault-secrets/)

## 4. Buildkite

Model Buildkite beda secara arsitektural dari 3 sistem di atas: **control plane adalah SaaS**, **penyimpanan secret direkomendasikan di luar Buildkite** (Vault/AWS Secrets Manager), bukan di sistem itu sendiri. Ini paling dekat dengan pola "secret store eksternal + agent yang tarik saat runtime" yang relevan untuk kami.

### 4.1 Penyimpanan
- **[VERIFIED-DOC]** Buildkite **secara eksplisit merekomendasikan untuk TIDAK menaruh secret utama di Buildkite** — pakai fitur "Buildkite secrets" hanya untuk kasus terbatas, dan integrasikan secret manager eksternal (AWS Secrets Manager, HashiCorp Vault) untuk kebutuhan skala organisasi.
- Ini konsisten dengan model SaaS: karena control plane bukan milik operator, menaruh kredensial jangka panjang di sana menambah pihak yang harus dipercaya. Bukan pola yang relevan untuk kami karena kami self-host penuh (control plane sendiri sudah trusted boundary yang sama dengan tempat Project/secret hidup).

### 4.2 Scoping
- **[VERIFIED-DOC]** Scoping lewat **cluster dan queue segmentation** — build di satu queue **hanya bisa akses secret yang memang dia butuhkan**. ⇒ mirip mekanisme least-privilege by-infrastructure-partitioning, bukan by-token-permission.
- Pemetaan ke model kami: queue Buildkite ≈ semacam partisi Runner-pool per Project — ide yang applicable: **Runner pool tidak perlu partisi fisik, tapi kredensial yang dikirim ke satu StepRun harus dibatasi ke Project StepRun itu**, bukan "semua secret yang pernah dikonfigurasi di instance".

### 4.3 Pengantaran ke Agent
- **[VERIFIED-DOC]** Agent (Runner) melakukan **outbound long-poll ke `agent.buildkite.com`** — tidak butuh inbound port sama sekali, cocok persis dengan model Runner kami di belakang NAT.
- **[VERIFIED-DOC]** Dua pola pengantaran secret yang didokumentasikan:
  1. **Environment hooks** (direkomendasikan) — secret di-export lewat *agent-level lifecycle hook* (script yang jalan di Runner, dikontrol operator Runner, **bukan** bagian dari `pipeline.yml` yang bisa diubah penulis pipeline) — sehingga job/pipeline author tidak bisa mengubah cara secret di-fetch atau mem-bypass agar secret keluar. Guidance eksplisit: hook ini "cannot be bypassed or avoided through a pipeline.yml modification."
  2. **Runtime injection** (fallback, tidak direkomendasikan) — secret di-inject saat build jalan; guidance eksplisit: **jangan simpan sebagai static env var** kalau pakai jalur ini.
- Pola #1 sangat relevan untuk kami: **secret-fetch logic dikontrol di level Runner/operator, terpisah dari apa yang StepRun/Agent bisa modifikasi** — ini prinsip pemisahan yang bisa kami tiru: kredensial masuk ke Sandbox lewat mekanisme yang tidak bisa diubah oleh instruksi di dalam StepRun (mis. prompt Agent), bukan diteruskan mentah sebagai bagian dari payload job yang bisa "dibaca ulang" atau dimanipulasi Agent.

### 4.4 Redaksi log — bagian kritis
- **[VERIFIED-DOC — jawaban langsung ke pertanyaan brief]** Redaksi terjadi **di sisi Agent (Runner), SEBELUM log diupload** ke Buildkite. Dari dokumentasi: nilai env var yang cocok pola diredaksi *"before the build log is uploaded to Buildkite"*. Log di-chunk oleh `LogStreamer` dan diupload lewat goroutine worker — redaksi terjadi di tahap pemrosesan chunk sebelum upload, bukan saat serve/render di server. Ini kebalikan dari GitHub Actions/Woodpecker (yang server-side) — **trade-off**: aman karena nilai mentah tidak pernah melintasi jaringan ke luar Runner, tapi **tidak bisa diperbaiki belakangan** kalau ada pola baru yang lolos (karena chunk yang sudah lolos filter sudah terupload tanpa sensor).
- **[VERIFIED-DOC]** Auto-redact default berbasis **pattern nama env var** (`*_PASSWORD`, `*_SECRET`, `*_TOKEN`, `*_PRIVATE_KEY`, `*_SSH_KEY`, `*_ACCESS_KEY`, `*_SECRET_KEY`, `*_CONNECTION_STRING`, `*_API_KEY`) + nilai yang diambil lewat command `secret get` bawaan. Untuk secret dari sumber eksternal (Vault dll), harus didaftarkan manual lewat `buildkite-agent redactor add`.
- **[VERIFIED-DOC — bug nyata, bukan hipotetis]** GitHub issue `buildkite/agent#3588` (dilaporkan, status open saat riset ini dibuat) mendokumentasikan **dua mode kegagalan konkret di produksi**:
  - **Pattern matching tidak di-anchor** — pola `*_SECRET` salah match ke `FAKE_SECRETS` (plural) karena tidak menjangkarkan akhir string, sebaliknya bisa juga *gagal* match kasus yang seharusnya cocok tergantung posisi wildcard — bug arah "greedy/tidak presisi".
  - **Nilai pendek (<6 byte) tidak diredaksi** — locus masalah yang sama seperti GitHub Actions (secret pendek sengaja/tidak sengaja lolos threshold minimum), dengan efek samping lucu tapi mengkhawatirkan: kata umum seperti `"true"` atau digit `1` malah ikut ter-redact secara salah (over-redaction) di satu jalur, sementara under-redaction terjadi di jalur lain — inkonsistensi antara command `pipeline upload --reject-secrets` dan `redactor` menunjukkan **dua implementasi terpisah yang tidak konsisten**, bukan satu source of truth.
  - **JSON dengan duplicate key** — parser JSON cuma menyimpan entry terakhir kalau ada key berulang, jadi kalau secret di-embed di JSON dengan key yang sama muncul dua kali, salah satu nilai bisa lolos dari daftar redaksi tanpa disadari.
- **Kesimpulan**: bahkan sistem dengan redaksi **client-side sebelum upload** (desain paling aman secara arsitektur) tetap punya kebocoran nyata di level implementasi (regex tidak presisi, threshold panjang, parsing JSON) — konfirmasi bahwa **redaksi berbasis pattern-matching tidak pernah cukup sebagai satu-satunya lapisan pertahanan**, terlepas dari di mana ia dijalankan.

### 4.5 Ancaman kode arbitrer
- **[VERIFIED-DOC]** Guidance resmi Buildkite eksplisit mengakui **pipeline bisa menjalankan kode arbitrer** dan merekomendasikan: batasi plugin ke yang private/version-pinned (mitigasi supply-chain), pasang *agent-level lifecycle hooks* yang **tidak bisa di-override lewat `pipeline.yml`** (garis pertahanan yang tidak bisa disentuh oleh apa yang job/pipeline eksekusi), dan jalankan security scanning wajib di semua build.

## 5. Concourse CI

Concourse **tidak punya secret store bawaan sama sekali** secara default — filosofinya "credential manager itu pluggable, resolve di runtime, jangan simpan di Concourse."

### 5.1 Penyimpanan
- **[VERIFIED-DOC]** Concourse mendukung credential manager eksternal: **HashiCorp Vault, CredHub, AWS SSM, AWS Secrets Manager**. Tidak ada penyimpanan secret internal default — kalau tidak dikonfigurasi ke salah satu backend ini, satu-satunya cara adalah taruh literal di pipeline YAML (tidak direkomendasikan, dan eksplisit didokumentasikan sebagai anti-pattern).
- **[VERIFIED-DOC]** Struktur: `web` node (ATC — control plane) yang mengautentikasi ke Vault/CredHub dan melakukan **lookup saat scheduling** (bukan disimpan lokal), pakai token atau auth backend yang dikonfigurasi di level operator instance.
- Ini pola paling "murni pull, zero storage": Concourse tidak pernah punya database secret miliknya sendiri untuk dijaga — ancaman "bocor dari database Concourse" tidak eksis by design karena tidak ada yang disimpan. Tapi ini memindahkan seluruh beban operasional (uptime, backup, akses) ke Vault/CredHub eksternal yang harus dijalankan terpisah — bukan gratis.

### 5.2 Scoping
- **[VERIFIED-DOC]** Path hierarkis: **`/concourse/<team>/<pipeline>/<secret>`**. Resolusi: kalau job scoped ke satu pipeline, ATC cari dulu di path pipeline, kalau tidak ketemu baru fallback ke path team. Team adalah unit isolasi tertinggi (mirip **Project** kami), pipeline di dalamnya lebih sempit (mirip Pipeline/Repository kami).
- Pemetaan cukup natural ke model kami: **team ⇒ Project**, pipeline path ⇒ sub-scope di dalam Project. Yang tidak ada padanannya: Concourse tidak punya konsep Principal (User vs ServiceAccount) terpisah dari team — semua yang beroperasi dalam satu team pakai jalur credential yang sama.

### 5.3 Pengantaran ke worker
- **[VERIFIED-DOC]** Arsitektur **TSA (Transport Security... — nama resminya custom SSH server untuk registrasi worker)**: worker (setara Runner kami) membuat **reverse SSH tunnel outbound** ke TSA (biasanya co-located dengan ATC, port 2222). Worker **tidak perlu internet-routable / tidak perlu inbound port** — worker yang inisiasi koneksi, TSA lalu membuka forwarded port lokal di sisi web node yang meneruskan balik ke Garden (container runtime) & Baggageclaim (volume store) milik worker itu. Heartbeat tiap 30 detik untuk deteksi worker stall.
- Ini pola arsitektur **paling dekat dengan yang kami butuhkan** untuk Runner outbound-only: bukan long-poll job queue (seperti GitHub Actions/Woodpecker/Buildkite), tapi **reverse tunnel persisten** yang membuat ATC bisa "menjangkau" worker seolah-olah worker itu servernya sendiri, padahal inisiasi selalu dari worker. Trade-off: kompleksitas operasional tunnel lebih tinggi dibanding pola long-poll sederhana.
- **[IMPRESSION]** Detail persis bagaimana nilai credential yang sudah di-resolve ATC dikirim ke task container di worker (lewat tunnel yang sama, sebagai bagian dari container spec Garden) tidak saya baca eksplisit di dokumentasi Vault credential manager — kemungkinan besar credential diinterpolasi ke dalam container spec oleh ATC lalu dikirim lewat tunnel yang sama ke Garden API, tapi ini dugaan arsitektural, bukan verifikasi baris-demi-baris ke source.

### 5.4 Redaksi log
- **[VERIFIED-DOC]** Concourse punya fitur **"Redacting credentials"** eksplisit (disebut di dokumentasi credential manager) — nilai yang diresolve dari credential manager otomatis di-mask di log task. Detail mekanisme presisi (di mana persis terjadi — ATC atau worker) tidak sempat saya verifikasi lebih dalam di sesi ini.
- **[VERIFIED-DOC — pola kegagalan operasional nyata, bukan bug redaksi log tapi bug *tooling* di sekitarnya]** Isu `concourse/concourse#646`: praktik umum `fly get-pipeline | fly set-pipeline` (dump config lalu apply ulang) **membocorkan credential** karena `fly get-pipeline` awalnya bisa menampilkan literal value yang seharusnya cuma referensi `((var))`. Fix/mitigasi resminya: pastikan semua credential direferensikan lewat `((var))` interpolation, bukan literal, sehingga `fly get-pipeline` hanya pernah menampilkan nama referensi, tidak pernah nilai — bug class ini (**tooling introspeksi/debug yang tidak sadar lagi menyentuh secret**) relevan banget untuk kami: **API/CLI debug apa pun di control plane kami (dump job config, replay StepRun, dsb) harus didesain agar tidak pernah bisa menampilkan nilai secret**, bukan cuma jalur log.

Sumber: [concourse-ci.org — Credential Management](https://concourse-ci.org/docs/operation/creds/), [concourse-ci.org — Vault credential manager](https://concourse-ci.org/docs/operation/creds/vault/), [github.com/concourse/concourse/tree/master/tsa](https://github.com/concourse/concourse/tree/master/tsa), [github.com/concourse/concourse/issues/646](https://github.com/concourse/concourse/issues/646)

### 6.2 Pola arsitektural yang berulang (semua 5 sistem, [VERIFIED-DOC] di semua kasus di atas)
- **Semua Runner/agent bersifat outbound-only** — tidak ada satu pun sistem yang mengharuskan control plane menghubungi balik ke runner. Dua sub-pola: **long-poll job queue** (GitHub Actions, Woodpecker, Buildkite, Drone) vs **reverse tunnel persisten** (Concourse TSA). Untuk Runner kami: long-poll lebih sederhana dioperasikan; reverse tunnel lebih cocok kalau butuh interaksi dua-arah yang sering (mis. streaming perintah interaktif ke Sandbox), tapi menambah kompleksitas signifikan. **Rekomendasi: mulai dari long-poll**, karena StepRun kami pada dasarnya "ambil kerja, jalankan, laporkan hasil" — pola yang sama seperti CI biasa.
- **Redaksi log terjadi di salah satu dari dua tempat, tidak pernah keduanya**: control-plane (GitHub Actions, kemungkinan Woodpecker) vs runner-side-before-upload (Buildkite). **Tidak ada sistem yang membuktikan satu tempat lebih superior** — Buildkite yang redaksi client-side pun tetap punya bug produksi nyata (issue #3588). Kesimpulan kami: **lokasi redaksi bukan pertanyaan yang paling penting** — pertanyaan yang lebih penting adalah **apakah pattern-matching-based redaction dipakai sebagai satu-satunya lapisan pertahanan** (jawabannya harus tidak).
- **Semua sistem yang mendokumentasikan redaksi eksplisit mengakui "tidak dijamin"** (GitHub: *"not guaranteed"*; Woodpecker: hanya secret dari store sendiri; Buildkite: bug nyata di threshold panjang & pattern anchoring). Tidak ada satu pun vendor CI mapan yang mengklaim redaksi berbasis regex/string-match itu complete — ini konsensus industri, bukan pendapat kami.
- **Scoping makin ketat makin baik menahan blast radius, tapi tidak ada sistem yang scoping-nya per-Principal** seperti model kami (User vs ServiceAccount dengan credential terpisah walau di Project yang sama). Semua sistem CI di atas scoping-nya per-**tempat kerja** (repo/org/team/queue), bukan per-**siapa yang menjalankan**. Ini gap desain yang genuinely baru untuk kami isi sendiri, bukan sesuatu yang bisa dicontek langsung.

### 6.3 Akses repo self-hosted git host (Gitea/Forgejo) — wajib dibahas terpisah

- **[VERIFIED-DOC]** Baik **Gitea** maupun **Forgejo** (fork Gitea) memberi tiap job Actions sebuah **token bawaan otomatis** (`GITEA_TOKEN` / setara di Forgejo), **di-scope ke repo tempat job berjalan saja** — akses ke repo lain (selain repo saat ini) ditolak (404), butuh PAT terpisah kalau memang perlu lintas-repo.
- **[VERIFIED-DOC]** Permission token ini **configurable per-job/workflow** (`permissions:` key) dan **di-clamp** terhadap batas maksimum yang dikonfigurasi admin instance — pola least-privilege-by-declaration yang sama seperti GitHub Actions asli (masuk akal, karena Gitea Actions memang didesain kompatibel sintaks dengan GitHub Actions).
- **[VERIFIED-DOC]** Dua mode permission: **Permissive** (default, read+write ke sebagian besar unit repo — backward-compatible tapi permisif) vs **Restricted** (read-only ke code/releases/packages, tanpa akses lain by default). **Untuk kami, mode Restricted-equivalent harus jadi default**, bukan opt-in, mengingat Agent yang jalan bisa dimanipulasi (lihat §7).
- **[VERIFIED-DOC]** PR dari fork **selalu dibatasi read-only** ke contents — perlindungan built-in terhadap kontributor eksternal yang mencoba modifikasi workflow untuk mencuri token. Kalau kami membuka model kontribusi eksternal/multi-tenant di masa depan, pola ini wajib ditiru.
- **[VERIFIED-DOC]** Forgejo secara eksplisit mendokumentasikan **runner sebagai unit trust yang bisa terkompromi permanen**: *"any future workflows sent to this [compromised] runner may also be compromised."* Rekomendasi resminya: **jangan share runner host antar-user/tenant yang tidak saling percaya**, dan container-based runner (bukan host-runner langsung) adalah minimum baseline isolasi — host-runner disebut eksplisit **"trivial to escape."**
- **[VERIFIED-DOC]** Secret Forgejo: **dienkripsi di database, dikirim ke runner hanya saat dibutuhkan (on-demand, bukan pre-loaded semua)** — pola pengantaran "just enough, just in time" ini sejalan dengan prinsip yang kami mau untuk Sandbox: Sandbox seharusnya hanya menerima credential Project yang relevan untuk StepRun itu, bukan seluruh koleksi secret Project di-mount sekaligus.
- Perbandingan operasional Gitea/Forgejo vs GitHub App token: **token bawaan Gitea/Forgejo sudah short-lived-per-job secara default tanpa perlu infrastruktur App terpisah** (tidak perlu bikin "GitHub App"-equivalent) — ini lebih murah dioperasikan untuk single-instance self-host seperti kami, dan **relevan langsung**: kalau kami membangun sendiri git-remote-access token issuance, pola paling sederhana yang terbukti dipakai production adalah **token per-job, di-generate saat StepRun mulai, di-scope ke Repository yang memang disentuh Pipeline itu, expire begitu StepRun selesai** — tidak perlu meniru kompleksitas GitHub App (yang dirancang untuk multi-tenant marketplace SaaS, bukan instance internal satu tim).

## 7. Agent yang bertingkah — ancaman baru vs CI biasa

**Jawaban singkat untuk pertanyaan brief: tidak ada satu pun dari 5 sistem CI klasik (GitHub Actions, Woodpecker, Drone, Buildkite, Concourse) yang punya threat model built-in untuk "agent yang membuat keputusan otonom berdasarkan konten yang tidak dipercaya."** Kelimanya didesain mengasumsikan skrip build **deterministik** — ancaman yang mereka antisipasi adalah "pipeline config ditulis penyerang" (mis. PR dari fork berisi `pipeline.yml` jahat), bukan "agent yang jalan dengan config jujur tapi dibujuk lewat konten yang dibacanya saat runtime." Ini beda kategori serangan.

### 7.1 Insiden nyata: Claude Code + GitHub Actions (CVE-2025-66032 / GHSA-xq4m-mc3c-vvg3) — **[VERIFIED-DOC, dari research note Cloud Security Alliance]**
Ini insiden paling relevan yang saya temukan — bukan CI klasik, tapi **persis pola ancaman kami**: AI coding agent (Claude Code) jalan di dalam GitHub Actions.

- **Bug akar**: fungsi otorisasi `checkWritePermissions` di `claude-code-action` menganggap **semua actor yang identity string-nya berakhiran `[bot]` otomatis terpercaya** — asumsi yang salah karena siapa pun bisa membuat GitHub App (yang otomatis dapat suffix `[bot]`) tanpa perlu write access ke repo.
- **Rantai serangan**: penyerang bikin issue di repo publik berisi instruksi tersembunyi (prompt injection) → Claude Code membaca isi issue sebagai instruksi otoritatif → dibujuk untuk `cat /proc/self/environ` → mengekstrak `ACTIONS_ID_TOKEN_REQUEST_TOKEN` dari environment → menukar token itu untuk **OIDC token dengan akses write** → push kode jahat ke repo yang jadi dependency proyek lain (supply-chain).
- **Kenapa ini kategori baru**: di CI klasik, isi *issue* bukan input yang pernah dieksekusi sebagai perintah. Di sini, **agent itu sendiri adalah interpreter** yang mengubah teks bebas (judul/isi issue, komentar PR) menjadi tindakan sistem (baca env, jalankan command, tukar token). Permukaan serangan bukan lagi "siapa yang bisa menulis `pipeline.yml`" tapi **"siapa yang bisa menulis teks yang akan pernah dibaca agent."** Untuk kami: itu berarti isi issue tracker, deskripsi task, komentar review, bahkan output tool (mis. hasil `grep` dari kode pihak ketiga) — semua adalah permukaan prompt-injection potensial terhadap Agent yang jalan di Sandbox kami.
- **Timeline**: disclosure awal 12 Jan 2026 (RyotaK/GMO Flatt Security) → fix Anthropic 16 Jan 2026 → disclosure publik 1 Jun 2026. Insiden serupa lain disebut ("Clinejection", 17 Feb 2026, pola sama di tool Cline) — menunjukkan ini bukan bug satu produk, tapi **kelas kerentanan berulang di ekosistem AI coding agent + CI**.
- **Mitigasi yang direkomendasikan** (dari research note): pin action ke commit SHA (bukan tag mengambang), hilangkan konfigurasi permissive seperti `allowed_non_write_users: "*"`, **sanitasi semua metadata eksternal (judul issue, deskripsi, komentar) sebelum masuk context agent**, wajib approval manusia sebelum tindakan hasil-agent dieksekusi (terutama push/deploy), egress filtering jaringan di level runner, least-privilege permission workflow.

### 7.2 Ancaman spesifik lain yang terdokumentasikan di ekosistem AI-agent-in-CI (2026) — **[IMPRESSION, kumpulan dari beberapa sumber pihak ketiga/riset keamanan, bukan satu source tunggal otoritatif]**
- **Allowlist command/tool bisa diracuni**: kalau ada mekanisme "command yang diizinkan tanpa approval", penyerang bisa mengarahkan agent memakai command yang *sudah* di-allowlist tapi dengan argumen/payload yang berbeda dari maksud aslinya — allowlist berbasis nama command saja tidak cukup.
- **Egress filtering berbasis SNI bisa dibypass**: laporan "Claude Code SOCKS5 proxy bypass" dan "sandbox network allowlist bypass" (dua laporan terpisah, kedua dari peneliti independen, bukan dari Anthropic sendiri) mengklaim proxy yang hanya memeriksa SNI/DNS pada filtering egress bisa dilewati kalau agent bisa mengarahkan traffic lewat kanal lain (proxy tersier, DNS tunneling, dsb.) — implikasi: **egress allowlist adalah mitigasi lapis, bukan jaminan absolut**, terutama kalau implementasinya splicing-tanpa-inspeksi-payload (lihat detail teknis di bawah).
- **Wildcard/misconfigured allowlist**: dilaporkan ada window ~5.5 bulan di mana konfigurasi sandbox Claude Code tertentu memakai wildcard yang secara efektif meniadakan boundary jaringan sama sekali pada sistem yang menyimpan credential — bukan bug logika filtering, tapi **kesalahan konfigurasi default/dokumentasi** yang baru diperketat belakangan (validasi karakter non-DNS seperti null byte, `%`, CRLF ditambahkan di fix).
- **Prinsip mitigasi yang paling sering direkomendasikan lintas sumber**: *"jangan taruh secret yang bisa di-exfiltrate di dalam Sandbox sama sekali kalau bisa dihindari"* — pakai **secrets broker per-command** (Sandbox minta credential spesifik saat mau dipakai, bukan semua credential Project di-preload sebagai env var yang bisa dibaca `printenv`), dan default-deny network egress dengan allowlist sesempit mungkin (bukan `github.com` luas, tapi endpoint API spesifik yang benar-benar dipakai).

### 7.3 Implikasi konkret untuk kami
1. **Redaksi log tidak menyelesaikan masalah utama.** Insiden nyata di atas tidak dimulai dari "secret bocor ke log" — dimulai dari **agent dibujuk untuk membaca secret dan mengirimkannya ke luar lewat jalur yang bukan log** (network call, commit message, push ke branch/repo yang dikendalikan penyerang). Redaksi log penting (dan sandcastle nol hasil untuk itu = harus diperbaiki), tapi **egress control dan scoping credential jauh lebih penting** untuk kelas ancaman spesifik agent.
2. **Isi apa pun yang bisa ditulis pihak luar (issue, PR description, comment, bahkan nama branch) dan akan dibaca Agent = permukaan serangan**, harus diperlakukan sama seperti "kode tidak dipercaya" walau bentuknya teks natural bahasa, bukan skrip.
3. **Approval gate untuk tindakan berdampak (push ke branch bukan branch StepRun-nya sendiri, akses ke Repository lain dalam Project yang sama, network call ke luar allowlist) adalah kontrol yang paling murah-untuk-manfaat** dibanding mencoba menyempurnakan redaksi/filtering yang terbukti berulang kali gagal di semua vendor.

Konteks: satu tim internal, self-host penuh, TypeScript + Postgres. Batas yang masuk akal — bukan daftar keinginan keamanan tanpa ujung.

### Minimum yang tetap wajib dibangun

1. **Enkripsi secret at-rest di Postgres, wajib ON, bukan opsional.** Woodpecker/Drone menjadikan ini opsional (default OFF) — itu preseden buruk, jangan ditiru. Pola paling murah-untuk-dibangun: satu master key (env var/secret file di-inject saat startup control plane, seperti pola Woodpecker/Drone) yang mengenkripsi kolom secret di Postgres (AES-GCM, sama seperti Drone/Woodpecker) — **tidak perlu Vault/KMS/HSM eksternal** di skala satu tim. Rotasi key: simpan `key_version` per baris secret supaya bisa re-encrypt bertahap kalau key pernah diganti — jangan bangun ini sekarang kalau belum ada kebutuhan konkret (YAGNI), cukup pastikan skema tabel tidak menutup jalan ke sana nanti (kolom `key_version` sejak awal cukup).
2. **Secret menempel ke Project, resolusi di scheduling time (pola Concourse), bukan pre-loaded ke semua StepRun.** StepRun hanya menerima secret Project yang benar-benar dipakai step itu — bukan seluruh koleksi secret Project di-mount sekaligus. Ini prinsip least-privilege paling murah dan paling berdampak dari seluruh riset ini.
3. **Token repo per-StepRun, short-lived, di-generate saat StepRun mulai, scope ke Repository yang disentuh Pipeline itu saja, expire saat StepRun selesai.** Tiru pola Gitea/Forgejo `GITEA_TOKEN` (built-in per-job, scoped, tanpa perlu infrastruktur App terpisah) — **bukan** pola GitHub App (dirancang untuk marketplace SaaS multi-tenant, over-engineered untuk instance internal). Untuk git host self-hosted (Gitea/Forgejo) ini API yang sudah tersedia; tinggal panggil saat StepRun mulai, revoke/biarkan expire saat selesai.
4. **Default-deny network egress dari Sandbox, allowlist sesempit mungkin** (endpoint API model, registry paket yang benar-benar dipakai) — bukan mitigasi sempurna (§7.2 menunjukkan bypass SNI-filtering pernah dilaporkan), tapi tetap satu-satunya kontrol yang menahan kelas serangan "agent dibujuk mengirim secret keluar lewat jalur bukan-log" yang justru paling relevan untuk kami (bukan skenario CI klasik).
5. **Redaksi log — minimum viable, bukan nol seperti sekarang di sandcastle.** Pattern-match berbasis nama variabel yang terdaftar sebagai secret (seperti semua 5 sistem di atas), dijalankan **sebelum log dipersist ke storage yang bisa dibaca user lain** (pola Buildkite: di Runner, sebelum upload — paling aman untuk arsitektur outbound-only kami karena StepRun/Sandbox yang paling tahu nilai mentah, bukan control plane). Terima bahwa ini akan tetap punya celah (base64, JSON reformat, dst — semua vendor punya masalah sama) — **jangan investasi berlebih menyempurnakan regex-matching**, itu bukan lapis pertahanan utama untuk ancaman agent (lihat §7.3 poin 1).
6. **Approval gate untuk tindakan berdampak tinggi**: push ke Branch/Repository di luar yang ditugaskan ke StepRun itu, akses ke Repository lain dalam Project yang sama, network call ke luar allowlist. Ini kontrol termurah-berdampak-tertinggi yang muncul berulang di riset §7 — lebih penting daripada menyempurnakan redaksi.
7. **Sanitasi/pelabelan konten eksternal sebelum masuk context Agent** — kalau Pipeline kami mengizinkan Agent membaca issue/PR description/comment dari luar (bukan hanya kode di repo), tandai eksplisit sebagai "untrusted input", jangan biarkan bercampur tanpa label dengan instruksi Pipeline yang trusted. Ini pelajaran langsung dari insiden CVE-2025-66032 (§7.1).

### Yang TIDAK perlu dibangun di skala ini

1. **Integrasi Vault/SOPS/age sebagai dependency wajib.** Semua sistem yang mewajibkan secret manager eksternal (Concourse, dan rekomendasi kuat Buildkite) melakukannya karena mereka SaaS multi-tenant atau enterprise besar dengan tim keamanan terpisah yang sudah mengoperasikan Vault untuk kebutuhan lain. Untuk satu tim internal self-host, **menambah Vault berarti menambah satu sistem lagi yang harus di-uptime-kan, di-backup, dan di-operate** — biaya operasional yang tidak sepadan manfaatnya di skala kami. Kalau nanti tim tumbuh atau ada requirement compliance eksternal, itu keputusan lain yang bisa diambil belakangan; jangan bangun sekarang untuk kebutuhan yang belum ada (YAGNI eksplisit dari brief).
2. **GitHub App-style installation token infrastructure.** Over-engineered untuk instance internal satu tim — token per-job sederhana (poin 3 di atas) cukup.
3. **Sistem revocation "cabut semua kredensial yang pernah lewat Runner X" yang otomatis dan canggih.** Tidak ada satu pun dari 5 sistem CI yang punya ini sebagai fitur satu-tombol (§1.6) — semuanya manual: deregister runner + rotate secret yang relevan. Untuk kami, cukup pastikan **daftar "Project mana saja yang pernah dilayani Runner ini" bisa di-query** (operability dasar), supaya rotasi manual saat insiden bisa dilakukan cepat dan lengkap — tapi tidak perlu membangun orkestrasi otomatis pencabutan massal sebelum ada insiden nyata yang membutuhkannya.
4. **Content-inspection payload untuk egress filtering (proxy MITM TLS penuh).** SNI-based filtering (pola Anthropic devcontainer) sudah cukup sebagai baseline dan jauh lebih murah dibangun/dioperasikan daripada MITM TLS penuh dengan cert authority sendiri. Terima keterbatasannya (§7.2), tapi jangan mulai dari solusi paling kompleks.
5. **Redaksi log yang mencoba menutup semua celah encoding (base64, URL-encode, JSON-reformat, dst) lewat aturan tambahan tanpa henti.** Setiap vendor besar sudah mencoba dan tetap punya celah (§4.4, §1.4) — ini medan yang secara fundamental tidak bisa "diselesaikan" lewat pattern-matching lebih banyak. Alokasikan effort itu ke kontrol §5 (approval gate) dan §4 (egress) yang punya batas ancaman lebih jelas, bukan ke lomba kucing-kucingan regex.

### Gap riset yang belum terverifikasi (jujur, bukan diklaim selesai)
- Mekanisme clone/push repo Woodpecker & Drone (tidak sempat diverifikasi ke dokumentasi resmi).
- Lokasi persis redaksi log di Woodpecker, Drone, dan Concourse (server vs runner-side) — hanya GitHub Actions dan Buildkite yang terverifikasi eksplisit.
- Detail payload job message GitHub Actions/Woodpecker (apakah secret benar-benar ikut dalam response long-poll yang sama, atau ada request kedua) — kesan dari artikel arsitektur pihak ketiga, bukan pembacaan source code langsung.
- Bootstrap/manajemen master encryption key Actions secrets di GitHub Enterprise Server (self-host) — tidak ditemukan dokumentasi publik yang cukup rinci dalam sesi riset ini.
