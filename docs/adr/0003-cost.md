# 0003 — Cost and token tracking: no estimates, no recomputation, no quota

Status: Accepted (implemented by issue #12 — Cost dan token tracking)

## Context

A member wants to see what a Run, a StepRun, a turn, and a Project cost —
and must never see a number that *looks* right but is made up. Two rules
shape everything, both about refusing fake figures (spec: "Cost"):

1. **Yang tidak ada tidak diperkirakan** — what does not exist is not
   estimated. An agent that reports no token usage displays "tidak
   didukung", never a guessed figure. The accepted consequence, stated in
   the UI: the Project total is a **lower bound, not a total**.
2. **Yang sudah ditulis tidak dihitung ulang** — what is already written is
   not recomputed. Cost is priced exactly once when a StepRun's turn ends
   and stored together with the `price_version` it was priced against; no
   display ever multiplies the price table again.

This ADR records the decisions that make those two rules structural, and
how the cost surface stays honest alongside the artifact/log surfaces
(ADR-0001, ADR-0002).

## Decisions

### The agent reports usage in its Output; the control plane prices it once at `/result`

The agent reports `input_tokens` / `output_tokens` inside the `done` arm of
its `<factory-output>` tag — an optional `usage` field on the shared Output
contract (issue 9's contract, extended here). The Runner forwards the whole
done arm as `output_data`; the control plane's `/result` gate validates it
against the same contract, extracts the usage, and prices it in the same
transaction that commits the terminal StepRun. The number is the agent's
*claim* — this issue does not read a billing API; it prices what the agent
reports and never estimates what it did not.

### Cost is written once per attempt, keyed `(step_run_id, attempt)`, insert-only

The cost table is insert-only, one row per attempt, with
`(step_run_id, attempt)` as the primary key. Retries are new attempts and
physically cannot overwrite a prior row; the idempotent `/result` replay
returns before pricing, so an attempt is never priced twice. "Kumulatif
lintas attempt" is therefore a plain `SUM` — there is no cumulative column
that a retry must remember not to touch. An attempt whose agent reported no
usage still gets a row (NULL `tokens`/`cost_usd`/`price_version`) so the
per-attempt breakdown — the tool for investigating a StepRun that keeps
failing — is complete.

### A `price_versions` table, insert-only, pinned by `price_version`

Pricing policy lives in a `price_versions` table (USD per one million
tokens). It is insert-only: a new price state is a new row, never an
UPDATE. At StepRun end the control plane looks up the current version —
the most recently effective row — prices the reported usage, and stores
`price_version` alongside the cost. A later price change cannot rewrite
history because nothing ever re-reads the price table for an already
written cost row. The initial version `v1` is seeded by the migration so
the table is never empty; operators append newer versions over time.

### Three aggregations, on their own endpoints, never riding the poll

Per-StepRun (with the per-attempt breakdown), per-Run, and per-Project are
three separate GET endpoints — deliberately not layered onto the 3-second
list poll. The per-Run endpoint serves the run-detail screen that already
carries the cancel button: while the Run is in flight (`runEnded: false`)
the total is the **running cost** — the sum of completed attempts so far —
so a runaway Run's burn rate is visible where the stop button is.

### Two attribution columns; the Project breakdown reflects the credential used

`runs.triggered_by_principal_id` and `runs.credential_principal_id` (issue
#8) are the two attribution columns; the cost is attributed to the
**credential** principal, so shared-credential usage is visible. The
per-Project aggregation groups by `credential_principal_id`.

### Retention: never expires

Cost rows live as long as their Run. No retention sweep touches
`step_run_costs` — retention is not a cost concern (spec: "tidak pernah
kedaluwarsa, seumur baris Run").

### No quota, stated nakedly

There is no cost quota and no automatic stop: one runaway Run can burn
credit to exhaustion and the system will not halt it. The designed
counterweight is the running cost shown live on the cancel-button screen —
visibility, not a guardrail. This is a deliberate refusal, not an
oversight: an enforcement mechanism was weighed and rejected because
nothing short of a hard ceiling could stop a burn, and a hard ceiling is a
policy decision the spec does not want the cost surface to invent
(spec: "Tanpa kuota, dinyatakan telanjang").

## Consequences

- The stored cost is the single source of truth for every display; a
  display cannot drift from the price table because it never reads it.
- The price table's integrity is append-only by construction, so
  `price_version` is truthful history.
- A failed turn still records a row — NULL when the agent reported no
  usage — so the per-attempt breakdown is complete, which is exactly what
  investigating repeated failures needs.
- The agent's reported usage is trusted as-is (the Runner is inside the
  trust boundary); the control plane prices it, it does not audit it.
- Because the totals never expire and the price table is insert-only, a
  Project's cost page grows monotonically — accepted, per the retention
  decision.
